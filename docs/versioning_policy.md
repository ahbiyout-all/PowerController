# PowerController 소프트웨어 버전 관리 정책 (Semantic Versioning Policy)

본 문서는 **PowerController** 프로젝트의 공식 소프트웨어 버전 관리 규약(Versioning Policy)을 정의합니다. 
본 프로젝트는 글로벌 표준인 **Semantic Versioning 2.0.0 (SemVer: MAJOR.MINOR.PATCH)** 체계를 엄격히 준수하여 변경 규모에 맞춰 3단계로 명확히 분리하여 버전을 관리합니다.

---

## 📌 1. 버전 번호 체계 (MAJOR.MINOR.PATCH)

버전 번호는 `X.Y.Z` 형식의 3자리 양의 정수로 표기합니다.

$$\text{Version} = \mathbf{MAJOR}.\mathbf{MINOR}.\mathbf{PATCH}$$

```
   v 2 . 9 . 1
     │   │   └─── PATCH : 하위 호환 버그 수정, 핫픽스, 스타일 교정, 경량 최적화
     │   └─────── MINOR : 하위 호환 신규 기능 추가, UI 컴포넌트 확장, 시스템 모듈 신설
     └─────────── MAJOR : 하위 호환성이 깨지는 대규모 아키텍처 개편, 파괴적 변경
```

---

## 🎯 2. 변경 규모에 따른 3단계 버전 산정 기준

| 단계 (Tier) | 표기 포맷 | 하위 호환성 (Compatibility) | 변경 규모 및 성격 (Scope) | 승격 시 규칙 (Rule) |
| :--- | :--- | :--- | :--- | :--- |
| **1️⃣ MAJOR** | `X.0.0` | **하위 호환성 파괴 (Breaking Changes)** | 대규모 아키텍처 개편, 통신 프로토콜/DB 스키마 파괴적 변경 | MINOR, PATCH를 `0`으로 리셋 |
| **2️⃣ MINOR** | `x.Y.0` | **하위 호환성 100% 보장 (Backward Compatible)** | 새로운 기능(Features) 추가, 신규 UI 모듈/엔진 탑재 | PATCH를 `0`으로 리셋 |
| **3️⃣ PATCH** | `x.y.Z` | **하위 호환성 100% 보장 (Backward Compatible)** | 버그 수정(Fixes), 핫픽스, 텍스트/스타일 교정, 내부 최적화 | PATCH만 +1 증가 |

---

### 1️⃣ MAJOR 버전 (`X.0.0`) - 대규모 아키텍처 및 파괴적 변경
* **정의**: 기존 버전과의 **하위 호환성이 깨지는(Breaking Changes)** 대규모 변경이나 핵심 아키텍처의 전면 전환이 일어날 때 증가합니다.
* **증가 시점 (Triggers)**:
  1. 데이터 저장 스키마의 비호환성 변경 (구버전 설정 파일과 역호환 불가)
  2. 핵심 네트워크 통신 프로토콜의 파괴적 변경 (소켓 프레임 포맷, 암호화 패킷 구조 전면 수정)
  3. 주요 런타임 플랫폼/아키텍처의 전면 전환 (예: CLI 전용 구조에서 하이브리드 GUI+네이티브 C/C++ DLL 엔진 전면 도입)
  4. 기존 핵심 API 또는 CLI 인터페이스가 제거되거나 매개변수 동작 방식이 완전히 바뀔 때
* **승격 규칙**: MAJOR 번호가 증가하면 MINOR와 PATCH 번호는 반드시 `0`으로 초기화됩니다. (예: `v1.9.5` ➔ `v2.0.0`)

---

### 2️⃣ MINOR 버전 (`x.Y.0`) - 신규 기능 및 대규모 모듈 추가
* **정의**: 기존 기능과의 **하위 호환성을 100% 유지하면서 새로운 주요 기능(Features)이나 인터페이스 확장이 추가**되었을 때 증가합니다.
* **증가 시점 (Triggers)**:
  1. 새로운 사용자 인터페이스 모듈/컴포넌트 추가 (예: 상단고정 컴팩트 위젯 5종 테마 및 실시간 커스터마이저 탑재)
  2. 새로운 독립 편의 기능 추가 (예: 매 정각 알림 차임벨 기능, 부팅/시작 시 오늘 예약 작업 브리핑 모달)
  3. 새로운 전원 제어 모드 및 예약 방식 신설 (예: 알람 모드, 10대 인기 스케줄 스마트 프리셋 통합)
  4. 설정 관리 트랜잭션/버퍼링 로직 신설 (예: 환경설정 취소/적용 안전 분리)
  5. 새로운 배포/설치 도구 탑재 (예: Inno Setup 6 인스톨러 배포 엔진 전환, 독립형 네트워크 스케줄러 기능 확장)
* **승격 규칙**: MINOR 번호가 증가하면 PATCH 번호는 반드시 `0`으로 초기화됩니다. (예: `v2.8.3` ➔ `v2.9.0`)

---

### 3️⃣ PATCH 버전 (`x.y.Z`) - 버그 수정 및 미세 최적화
* **정의**: 기존 기능 및 하위 호환성을 유지하며 **버그 수정(Bug Fixes), 핫픽스, UI 텍스트/라벨 교정, 가벼운 성능 최적화, 사소한 스타일 조정**이 이루어졌을 때 증가합니다.
* **증가 시점 (Triggers)**:
  1. 예외 상황(Error/Crash/Hang) 방지 및 버그 픽스 (예: 원격 무인 설치 시 프로세스 미종료 및 파일 락 멈춤 완벽 해결)
  2. 다국어 번역 문구 교정 및 오탈자 수정 (예: 한국어/영어 라이선스 전문 분리 및 문구 교정)
  3. 간격, 여백, 아이콘 정렬 등 마이너 CSS/UI 스타일 미세 조정
  4. 내부 코드 리팩토링 및 빌드 워크플로 CI/CD 스크립트 인코딩 보정 (외부 기능 동작 및 인터페이스 영향 없음)
* **승격 규칙**: PATCH 번호만 1씩 증가합니다. (예: `v2.9.0` ➔ `v2.9.1`)

---

## 📋 3. 버전 동기화 및 단일 원천 (Single Source of Truth) 프로세스

프로젝트 코드 베이스에 변경사항이 발생하여 버전을 승격할 경우, **`package.json`의 `version` 필드를 단일 원천(Single Source of Truth)**으로 삼아 전체 구성 요소를 일괄 동기화합니다.

```
                  ┌───────────────────────────────┐
                  │ package.json (version: X.Y.Z) │ ◀── Single Source of Truth
                  └───────────────┬───────────────┘
                                  │
          ┌───────────────────────┼───────────────────────┐
          ▼                       ▼                       ▼
┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
│ Python 메인 엔진  │   │ Inno Setup & 빌더 │   │ React UI & 메타   │
│ - main.py         │   │ - PowerController │   │ - src/types.ts    │
│ - installer.py    │   │   .iss            │   │ - index.html      │
│ - network_...     │   │ - version_*.txt   │   │ - metadata.json   │
└───────────────────┘   └───────────────────┘   └───────────────────┘
```

### 🛠️ 버전 승격 체크리스트
1. **변경 규모 분석**: 발생한 작업이 MAJOR / MINOR / PATCH 중 어느 규모에 해당하는지 결정.
2. **`package.json` 버전 수정**: `version` 필드를 신규 버전 번호로 갱신.
3. **일괄 동기화 스크립트 실행**: `python scripts/sync_version.py`를 통해 모든 코드 및 메타데이터 동기화.
4. **`docs/patch_notes.md` 기록**: 신규 버전 번호, 릴리즈 일자, 변경 내역(Features, Improvements, Fixes) 작성.
5. **GitHub 커밋 & 태그 푸시**: `push_to_github.bat`을 실행하여 `git tag -a vX.Y.Z` 자동 생성 및 GitHub Releases 배포.
